## Evidence-backed strengths

- The same five-field Legacy payload operates in explicit `classical` and
  `mlkem` modes, keeping modernization at the Gateway--Cloud boundary.
- The secure path uses the frozen ML-KEM-768, HKDF-SHA-256, AES-256-GCM, and
  four-field-AAD contract, with contract and integration regression coverage.
- Tampered secure messages are rejected before storage, and secure failure is
  fail closed without automatic baseline fallback.
- Retries are bounded; an ordinary ambiguous-response retry resends the same
  already-built envelope and Cloud idempotency leaves one logical row.
- Compose, health/readiness endpoints, structured logs, and metrics provide a
  course-scale test and demonstration environment.

## Evidence-backed weaknesses and limits

- The Legacy boundary is unauthenticated and the controlled deployment uses
  HTTP; Cloud public-key distribution has no production identity mechanism.
- Gateway sequence state, secure sessions, and the Cloud ML-KEM key pair are
  in memory. Restarts require recovery and Cloud restart changes its key ID.
- SQLite, single instances, and bounded retries are suitable for the course
  environment but not high-availability production use.
- Protocol version 1 has no dedicated cryptographic anti-replay counter or window. `UNIQUE(device_id, sequence_number)` is business idempotency, not cryptographic replay protection.
